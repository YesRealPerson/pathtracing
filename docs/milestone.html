Summary of Current Progress

  • Most features of the CPU path tracer adapted to CUDA to be run on the GPU
    • Camera ray generation: one thread per pixel
    • BVH traversal and Ray-triangle intersection
    • BSDF and light sampling
    • Direct Lighting
  • Made changes to the setup to be GPU optimal
    • Flattening scene objects and moving entire scene from CPU to GPU alongside framebuffer
      • Primitives are plain structs with no pointers and BSDFs are uniquely copied and referenced via an id
    • Kept same algorithms as CPU implementations but replaced BVH traversal with iterative loop with a thread stack
      • No pointers in BVH, data for bbox, primitives, and nodes are indexed in arrays

GPU Flattening Approach

  • Polymorphism is bad (for GPUs)!
    • We want to be able to read everything related to a scene at once and be able to simply index across them
    • The starter code uses a lot of polymorphism to have unique features e.g. intersect for spheres vs triangles
  • Adapt shared features to single reusable struct
  • Use switch statements for child specific behavior (such as f for BSDFs or sample_L for lights)
    • GPU equivalents for a couple sampling functions
    • GPU intersection tests
    • Generally painless copying and pasting from the CPU pathtracer

Example: Primitives (Triangles, Spheres)

  • Use a type enum, and vectors for triangle points and normals.
  • Reuse same vectors to represent origin, radius and radius squared (we use x and y in the b vector).

Most objects have a new toGPU function which per instance creates a GPU equivalent struct.

BVH Construction + Intersection

A BVH is built by having a vector of bboxes, nodes, and order(primitive indices)

  • Index into these arrays is how a bvh is traversed instead of recursion
  • Uses the same midpoint of longest axis of centroid algorithm as our CPU implementation
  • Left and right are indexes into the nodes array of a node and root is at index 0
  • Leaves store a range of primitives

When a GPU scene is uploaded, it builds a BVH which adds the primitives and a order vector which keeps track of prims

Since each GPU thread has its own stack, we set a maximum stack size per GPU thread for BVH intersection

The algorithm is the same but the stack contains the indexes of the bvh nodes that we are checking for intersections

GPU Scenes

In total we make GPU equivalents for the following

  • Primitives, BVH Nodes, BSDFs, Lights, and Cameras

We centralize these into a GPUScene struct

  • (besides cameras, since there’s only one so we just pass it in at render time)

Everything is then uploaded to the GPU using an upload function which mallocs enough space for every primitive, BVH node, unique BSDF, and light.

We also have an equivalent free function.

Rendering is relatively painless once we’ve done all this setup!

All we effectively had to do was copy and paste our CPU rendering steps for zero and single bounce (importance) lighting and replace all references to CPU structs!
